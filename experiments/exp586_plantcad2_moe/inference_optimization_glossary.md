# Plotted inference optimizations

This is the legend for the accepted milestones in the three optimization-progress figures. Each row describes one **backend + optimization** pair. Repeated batch-size milestones are consolidated within their backend. Baselines and confirmation rows are included so every label in the plot tables is accounted for, although they are measurements rather than optimizations.

The plots are cumulative: a milestone is the best configuration observed at that point, including all retained earlier changes. Its throughput increase is therefore not necessarily an isolated estimate of that optimization's effect. Failed candidates marked with `×` are intentionally outside this glossary.

Implementation surfaces mean:

- **Framework:** public framework or tokenizer configuration and ordinary application code.
- **Model-specific:** code specialized to the d768 Grug/Hero architecture or this fixed ACGTN workload.
- **Runtime-specific:** compiler, kernel, scheduler, or engine hooks that may change across releases.
- **Measurement:** a baseline, repeat, or final confirmation rather than an optimization.

## PyTorch

| Plot milestone | What changed | Implementation surface |
|---|---|---|
| Full-vocabulary eager | Deliberately naive baseline. The [full-head branch](src/exp586_moe/inference/torch_backend.py#L874-L882) multiplies every hidden state by all 128,256 language-head rows and only then slices out A/C/G/T. It establishes the cost of using the exported language model literally; the large unused projection is part of the timed path even though only four columns reach the caller. | Measurement |
| A/C/G/T output head | Changes where the same selection occurs in the [head implementation](src/exp586_moe/inference/torch_backend.py#L874-L882): it gathers the four trained A/C/G/T weight rows first, then performs a four-output linear projection. This preserves the requested logits exactly while avoiding both the arithmetic and intermediate tensor for 128,252 unused vocabulary entries at every one of the 8,192 positions. | Framework |
| Grouped MoE kernels | Replaces the [naive execution loop](src/exp586_moe/inference/torch_backend.py#L750-L765), which iterates over all 384 experts in Python, finds the tokens routed to each expert, launches that expert's gate, up, and down matrix multiplications separately, and scatter-adds its weighted results. The [grouped path](src/exp586_moe/inference/torch_backend.py#L222-L255) expands every token into its eight token/expert assignments, sorts them into contiguous expert groups, and marks the group boundaries. Three `torch._grouped_mm` calls then execute all experts' gate, up, and down projections as grouped GPU work before one weighted scatter-add. Routing and expert math are unchanged; grouping removes hundreds of small launches and CPU dispatch decisions, giving the H100 substantially larger units of work. | Model-specific |
| Compile model | Replaces one eager Python-dispatched forward with the [fixed-shape compiled wrapper](src/exp586_moe/inference/benchmark_torch.py#L129-L141): `torch.compile(fullgraph=True, dynamic=False, mode="reduce-overhead")`. The 8,192-token length and trial batch are static, so Inductor can fuse elementwise work, specialize shapes, and remove repeated dispatcher overhead; compilation and warmup remain outside the throughput measurement. | Runtime-specific |
| Direct HF tokenizer | The baseline invokes `PreTrainedTokenizerFast`, which builds a Transformers-style result object and converts it to a tensor. The [direct path](src/exp586_moe/inference/benchmark_torch.py#L157-L171) calls the underlying Rust `tokenizers.Tokenizer`, reads its IDs, and constructs the tensor directly. Token IDs and character segmentation are unchanged; the gain comes from removing Python wrapper and output-format work for every batch. | Framework |
| Reduced HF tokenizer | Replaces the 128,256-entry BPE segmentation model with a [small character tokenizer](src/exp586_moe/inference/tokenizer.py#L44-L68). It retains the checkpoint's exact ACGTN token IDs and lowercase normalizer, so embedding lookup is identical, but it no longer searches language merge candidates for inputs guaranteed to contain only ACGTN. | Framework |
| Local FlexAttention | The previous local layers used SDPA with expanded query-head K/V tensors and a dense 8,192×8,192 mask. The replacement [precomputes a sliding-window block mask](src/exp586_moe/inference/torch_backend.py#L503-L528) and sends local layers through [FlexAttention](src/exp586_moe/inference/torch_backend.py#L619-L628), allowing blocks outside the causal window to be skipped rather than represented as masked dense work. | Runtime-specific |
| Global FlashAttention | The zero-stride K/V expansion used for grouped-query attention could push global layers onto a slow unfused fallback. The [global path](src/exp586_moe/inference/torch_backend.py#L567-L585) materializes only those K/V views, then [forces the FlashAttention SDPA backend](src/exp586_moe/inference/torch_backend.py#L637-L654). This trades a small copy for a fused Hopper attention kernel over the expensive full-context layers. | Framework |
| Increase batch / Retune batch | Each material graph change alters memory pressure and the balance between CPU, launch, and GPU work, so batch size is [explicitly swept and timed](src/exp586_moe/inference/benchmark_torch.py#L212-L268) again rather than inherited. The accepted plotted sizes move through 4, 8, 224, 128, 224, 16, 128, 192, and finally 240. Larger batches amortize tokenization, launch, and host-transfer costs, but the largest fitting batch is not assumed to be fastest. | Framework |
| Fused MoE | Replaces the three native grouped GEMMs and explicit scatter with vLLM's [packed `fused_experts` call](src/exp586_moe/inference/torch_backend.py#L712-L737). Gate and up weights are packed in the format expected by the Triton kernel, while selected experts and router weights are passed directly. This keeps expert gather, SwiGLU evaluation, weighting, and combine inside a kernel family tuned for routed MoE shapes. | Runtime-specific |
| Tokenizer pipeline | Serial execution tokenized batch *n+1* only after batch *n* had returned its host logits. The [one-worker pipeline](src/exp586_moe/inference/benchmark_torch.py#L239-L259) starts the next CPU tokenization job before launching the current GPU forward, then measures adjacent completed outputs so one-time pipeline fill is excluded. It hides tokenizer time whenever the GPU stage is longer and keeps tokenizer work inside the reported end-to-end rate. | Model-specific |
| Specialized router top-k | Generic `torch.topk` handles arbitrary widths and values, while this router always chooses eight of 384 FP32-biased logits. The [one-warp Triton kernel](src/exp586_moe/inference/torch_topk.py#L54-L112) assigns one program to each token row, compares bitwise-order-preserving keys in fixed tiles, and emits stable expert indices without producing unused values. The [router call site](src/exp586_moe/inference/torch_backend.py#L687-L704) still gathers the original unbiased logits and computes the same sigmoid/renormalized combine weights, so only selection machinery changes. | Model-specific |
| Direct short convolution | The prior path [transposed, padded, flipped weights, and invoked grouped `conv1d`](src/exp586_moe/inference/torch_backend.py#L194-L199) for a fixed four-tap depthwise causal filter. The [direct branch](src/exp586_moe/inference/torch_backend.py#L186-L193) writes the exact recurrence as four shifted multiply-adds. Inductor can fuse that fixed expression with surrounding work, avoiding the generic convolution layout transformations and setup while preserving lag-zero-first rounding closely enough for the correctness gate. | Model-specific |
| Batched HF tokenizer | Earlier direct-tokenizer trials still called `encode` once per sequence in Python. The [batched implementation](src/exp586_moe/inference/tokenizer.py#L82-L97) calls `encode_batch` once and lets the Rust/Rayon tokenizer schedule the entire batch, then converts the rectangular result directly to an integer array. This reduces Python crossings and exposes parallel CPU work, especially at the larger GPU batches. | Framework |
| FlashAttention 3 + native GQA | The earlier attention paths either expanded each KV head to every query head or relied on generic SDPA dispatch. The [FA3 path](src/exp586_moe/inference/torch_backend.py#L586-L618) packs independent 8,192-token sequences, leaves K/V at their native grouped-query head count, supplies cumulative sequence offsets, and calls vLLM's Hopper FlashAttention kernel. It avoids materializing repeated K/V tensors and uses the kernel tuned for H100 long-prefill attention. | Runtime-specific |
| Precompute rotary tables | The original [RoPE helper](src/exp586_moe/inference/torch_backend.py#L202-L219) rebuilds positions, inverse frequencies, angles, sine, and cosine for each call. Because every input is exactly 8,192 tokens, the optimized model [registers fixed sine/cosine buffers once](src/exp586_moe/inference/torch_backend.py#L482-L502) and the layer path only performs the rotations. This removes repeated transcendental work from every local-attention layer. | Model-specific |
| Combine shared-expert gate/up | Each of the two always-on shared experts previously launched separate gate and up linear layers. The replacement [concatenates each expert's two input weights at load time](src/exp586_moe/inference/torch_backend.py#L424-L438), then [splits one linear result](src/exp586_moe/inference/torch_backend.py#L800-L813) before the same SiLU product and down projection. It halves input-projection launches for the shared experts without changing their outputs. | Model-specific |
| Shared GEMMs (short run) | Extends the previous idea across both shared experts. Their gate/up weights and down weights are [packed into two layer-wide matrices](src/exp586_moe/inference/torch_backend.py#L439-L467); the [combined evaluator](src/exp586_moe/inference/torch_backend.py#L258-L273) performs one input projection, applies each expert's SwiGLU to its slice, concatenates the activations, and performs one output projection. Four input GEMMs and two output GEMMs become two larger GEMMs per layer. | Model-specific |
| Freeze graph (short run) / Freeze inference graph | The ordinary compiled graph still treats loaded parameters as runtime inputs. The final interface sets [`TORCHINDUCTOR_FREEZING=1` before importing Torch](src/exp586_moe/inference/optimized_torch.py#L1-L12), then builds one [static full-graph callable](src/exp586_moe/inference/optimized_torch.py#L60-L68). Inductor can regard weights and inference-only state as constants, fold more graph structure, and reduce runtime argument/guard work; the second plotted row repeats the full configuration longer at batch 240. | Runtime-specific |
| Long-run confirmation | This is not another optimization. The selected configuration was restarted in three fresh processes and run for more iterations; their median and range are preserved in the [final confirmation summary](results/inference_optimization/final-confirmation-summary.json). The median supplies the 1,584,801 tok/s headline and reduces the chance that a favorable short run becomes the reported result. | Measurement |

## vLLM

| Plot milestone | What changed | Implementation surface |
|---|---|---|
| Naive eager, full vocabulary | vLLM already provides fused attention, fused MoE, request scheduling, and memory management, so this baseline is less naive than the framework baselines. Its custom capture hook nevertheless follows the [full-head branch](src/exp586_moe/inference/benchmark_vllm.py#L128-L144), applying all 128,256 language-head rows to every prompt state before slicing A/C/G/T. It measures the serving engine with the same deliberately wasteful output projection. | Measurement |
| Project only A/C/G/T | At hook installation, the code [gathers the four trained head rows once](src/exp586_moe/inference/benchmark_vllm.py#L50-L53). During each prefill it applies only that four-row matrix in the [A/C/G/T branch](src/exp586_moe/inference/benchmark_vllm.py#L128-L145). Hidden states, engine execution, and returned probabilities are unchanged; the full language projection and its large temporary disappear. | Model-specific |
| + compile engine | The baseline sets `enforce_eager=True`. This milestone switches the [vLLM construction](src/exp586_moe/inference/benchmark_vllm.py#L394-L430) to `enforce_eager=False`, allowing vLLM/TorchInductor to compile supported model regions and use its normal optimized execution plan after warmup. The experiment keeps engine startup and compilation outside the timed region. | Runtime-specific |
| + reduced HF tokenizer | Replaces BPE segmentation with the same [ID-preserving ACGTN character tokenizer](src/exp586_moe/inference/tokenizer.py#L44-L68) used by Torch. vLLM still receives ordinary `prompt_token_ids`; only the host-side construction becomes simpler because inputs cannot contain language substrings or require merge search. | Framework |
| + tuned Triton MoE kernel | Selects vLLM's fused Triton MoE path and the better block-M candidate for this model's 384 routed experts. The benchmark can inject a tile through vLLM's [`override_config`](src/exp586_moe/inference/benchmark_vllm.py#L128-L136), which controls how routed token rows are grouped into expert GEMM blocks. The gain is modest because vLLM's baseline already used a fused expert implementation; this step tunes its launch shape rather than replacing a Python loop. | Runtime-specific |
| Increase batch | The outer benchmark sends more unique requests in each `generate` call using the [batch construction and engine invocation](src/exp586_moe/inference/benchmark_vllm.py#L450-L498). Accepted local batches move from 1 to 4, 32, 192, 224, 236, and 240. Larger calls amortize RPC, scheduler, tokenization, and output-capture overhead, but later experiments separate the queued request count from the active scheduler limit. | Framework |
| FlashAttention 2 + batch | Configures the engine's [attention backend and version](src/exp586_moe/inference/benchmark_vllm.py#L394-L424) explicitly as `FLASH_ATTN` version 2 while raising the batch to 32. This prevents backend auto-selection from choosing a less suitable long-prefill kernel and gives FA2 enough concurrent 8,192-token sequences to amortize engine overhead. Because both settings changed in this plotted milestone, its increase is cumulative rather than an isolated FA2 estimate. | Runtime-specific |
| Right-size KV cache + batch | The generic serving engine reserves KV memory for generation workloads, but this benchmark performs one 8,192-token prefill followed by only the required one-token completion. The milestone passes an [explicit roughly 8 GiB cache and active-sequence limit](src/exp586_moe/inference/benchmark_vllm.py#L394-L410), freeing HBM for a 256-request batch without relying on the default utilization heuristic. | Runtime-specific |
| Batch + overlap HF tokenization | Replaces per-sequence encoding with the [batched list encoder](src/exp586_moe/inference/tokenizer.py#L100-L114), then uses a [one-worker prefetch pipeline](src/exp586_moe/inference/benchmark_vllm.py#L510-L526) to build prompt dictionaries for batch *n+1* while vLLM executes batch *n*. This hides CPU character tokenization and Python prompt construction while retaining both in the measured completion interval. | Model-specific |
| Specialized router top-k | Monkey-patches the model's router with the [fixed-shape inference implementation](src/exp586_moe/inference/benchmark_vllm.py#L74-L99). It invokes the [one-warp 384-wide Triton selector](src/exp586_moe/inference/torch_topk.py#L54-L112), discards the extra training threshold candidate, and then computes the original sigmoid and 2.5-sum normalization from unbiased logits. Expert choices and weights remain equivalent; general routing statistics and selection machinery leave the hot path. | Model-specific |
| FlashAttention 3 | Changes only the [version passed to vLLM's `FLASH_ATTN` backend](src/exp586_moe/inference/benchmark_vllm.py#L413-L424), moving the same causal prefill operation from FA2 to the Hopper-specific FA3 implementation. The workload is almost entirely long prefill, so H100 tile scheduling and native grouped-query support matter more here than decode-oriented features. | Runtime-specific |
| Throughput peak | This is a local tuning marker rather than a new kernel. It records the best boundary from the batch/KV-cache sweep before scheduler restructuring: 240 queued and active requests with the explicitly sized cache. The row makes the later gains from chunking, scheduler budgets, and output transfer distinguishable from the earlier model-kernel work. | Measurement |
| Direct sconv + explicit MoE tile | The stock short-convolution module supports mixed prefill/decode metadata and general sequence shapes. The hook [recognizes pure 8,192-token prefills](src/exp586_moe/inference/benchmark_vllm.py#L101-L126) and dispatches a [fixed-length Triton four-tap kernel](src/exp586_moe/inference/torch_sconv.py#L9-L76), falling back for any other request. In the same milestone, `override_config` supplies explicit fused-MoE block sizes, warps, and stages. Specializing both hot kernels removes general serving branches for this exact workload. | Runtime-specific |
| Long-repeat confirmation | This repeats the same direct-sconv and explicit-MoE-tile configuration for more iterations. It tests whether the short candidate was a stable sustained rate before its settings were carried into later scheduler experiments; it does not add a new execution feature. | Measurement |
| Chunked prefill + direct sconv | Enables [`enable_chunked_prefill`](src/exp586_moe/inference/benchmark_vllm.py#L394-L410) while retaining the direct short-convolution hook. Instead of requiring all queued 8,192-token prompts to enter one monolithic scheduler step, vLLM can admit bounded prompt chunks under its token budget. This increases scheduling flexibility and lets long prefills coexist in a GPU-sized work set without changing prompt logits. | Runtime-specific |
| Limit scheduler to 262k tokens | Previously the default budget was derived from `batch_size × 8,193`, so a large request batch could authorize an enormous engine step. The [`max_num_batched_tokens` setting](src/exp586_moe/inference/benchmark_vllm.py#L394-L406) caps a step at 262,144 prompt tokens, about 32 complete windows. Bounded steps improve kernel-sized work and prevent queue size from directly dictating HBM demand. | Runtime-specific |
| Increase request batch | After chunking, `batch_size` is the outer request set passed to one engine call. The benchmark [configures request count separately from the token budget](src/exp586_moe/inference/benchmark_vllm.py#L374-L410), so sets of 264, 416, 512, and 768 keep the scheduler fed while `max_num_batched_tokens` limits the prompt chunks admitted to a step. These milestones leave `max_num_seqs` at the request count; the token budget, rather than a separate 64-request cap, bounds practical concurrent token work. | Framework |
| Transfer BF16 logits | The normal capture converts the four logits to FP32 before copying them to the host. This candidate uses the [BF16 transfer branch](src/exp586_moe/inference/benchmark_vllm.py#L145-L182), halving D2H bytes and converting back to FP32 afterward. It passed the probability/loss gate and briefly improved throughput, but the final path restores direct FP32 output because later overlap and buffer reuse made the precision change unnecessary. | Model-specific |
| Tune scheduler to 196k tokens | Repeats the bounded-step experiment with 196,608 tokens, equivalent to about 24 complete windows, while retaining a 512-request outer queue. The mechanism is the same [`max_num_batched_tokens` control](src/exp586_moe/inference/benchmark_vllm.py#L394-L406); this point measures whether smaller, more frequent engine steps better overlap scheduling and output capture. | Runtime-specific |
| 245k-token scheduler (short run) | Tests the intermediate 245,760-token budget, exactly 30 complete windows, with a 768-request queue. It balanced H100 work size against scheduler cadence better than 196k or 262k and became the [selected interface default](src/exp586_moe/inference/optimized_vllm.py#L47-L60). The plotted row is short, so the later confirmation supplies the headline. | Runtime-specific |
| Overlap output transfers | The synchronous branch calls `.cpu().numpy()` for every captured chunk, forcing GPU completion before engine progress continues. The replacement allocates pinned host tensors and issues [nonblocking copies as chunks finish](src/exp586_moe/inference/benchmark_vllm.py#L159-L178), then performs [one synchronization per engine batch](src/exp586_moe/inference/benchmark_vllm.py#L220-L235). D2H transfer can therefore overlap later GPU chunks, which matters because every sequence returns 8,192×4 FP32 values. | Runtime-specific |
| Increase request queue | Raises the outer request set from 768 to 1,536 while leaving the 245,760-token scheduler budget unchanged. The larger call reduces refill/RPC frequency and gives the scheduler more ready chunks, while the budget still caps each step at 30 windows' worth of tokens. A separate 64-request active cap is introduced only later with pinned-buffer reuse. | Framework |
| Reach request-queue plateau | Raises the queue again to 2,048 under the same active-work limits. The small remaining gain indicates queue refill overhead is nearly amortized and that scheduler budget, active sequence count, model compute, or output transfer now sets throughput. This row is a saturation measurement rather than a different algorithm. | Measurement |
| Reuse pinned output buffer | The asynchronous candidate allocated a new pinned destination for every captured chunk. The final hook [allocates one batch-sized pinned tensor](src/exp586_moe/inference/benchmark_vllm.py#L59-L72) and [copies each capture into the next slice](src/exp586_moe/inference/benchmark_vllm.py#L151-L158), resetting the offset between engine calls. This preserves nonblocking D2H behavior while removing repeated pinned-memory allocation and fragmentation; `max_num_seqs=64` limits active engine work independently of the 2,048-request queue. | Runtime-specific |
| Long-run confirmation | No new optimization is introduced. Three fresh processes run the final queue-2,048, active-64, 245,760-token-budget configuration and report their median and range in the [final confirmation summary](results/inference_optimization/final-confirmation-summary.json). The median supplies the 1,240,392 tok/s headline. | Measurement |

## JAX

| Plot milestone | What changed | Implementation surface |
|---|---|---|
| Full-vocabulary head | Deliberately naive XLA baseline. The [full-head executable](src/exp586_moe/inference/jax_backend.py#L286-L304) performs a `[batch, 8192, hidden] × [hidden, 128256]` einsum in FP32 accumulation and materializes the full result before the benchmark slices A/C/G/T. It measures the cost of applying the language model literally rather than the four-logit workload. | Measurement |
| A/C/G/T output head | The [reduced executable](src/exp586_moe/inference/jax_backend.py#L306-L325) gathers four trained output columns first and contracts hidden states only with that `[hidden, 4]` matrix. The requested logits are identical, but XLA no longer computes or materializes the other 128,252 outputs. Because the naive full projection dominated JAX, this produces the largest single jump in the experiment. | Framework |
| Increase batch / Retune batch | JAX compiles a separate fixed-shape executable for each batch, so the optimum changes after tokenizer, attention, router, and shared-expert graph changes. The [benchmark constructs and times fixed batches](src/exp586_moe/inference/benchmark_jax.py#L143-L203) at 1→2→4→8→16→32→64→256, then 128→224, and later 128→352. Larger batches amortize dispatch and host transfer, while the 95% memory pool allows the final 352 batch without assuming that maximum occupancy is automatically fastest. | Framework |
| Overlap HF tokenization | Serial JAX scoring waited for `encode_batch` before every device call. The [prefetch loop](src/exp586_moe/inference/benchmark_jax.py#L159-L190) tokenizes batch *n+1* on one CPU worker while batch *n* executes and copies logits to NumPy, measuring adjacent output completions to exclude initial fill. This cumulative milestone also [physically gathers five embedding rows and four output columns](src/exp586_moe/inference/jax_backend.py#L233-L251); after the output GEMM was already narrow, most of the observed gain came from hiding host tokenization rather than the smaller stored arrays. | Model-specific |
| Specialized router top-k | The training-derived router used `jax.lax.top_k`, which returns both values and indices for a general shape. The [inference revision](src/experiments/grug/moe_hero_ep/model.py#L1009-L1025) calls Levanter's indices-only `top_k_indices` for the 384-wide router and gathers only the selected logits needed for combine weights. It preserves top-8 expert choices and trained weighting while avoiding an unused top-values result at every token and MoE layer; at this stage it still selects a ninth threshold candidate for training statistics. | Model-specific |
| Inference-only routing | The next step removes the remaining training diagnostics. The compiled forward passes [`collect_router_metrics=False`](src/exp586_moe/inference/jax_backend.py#L286-L325), which makes the [router request exactly K rather than K+1 experts](src/experiments/grug/moe_hero_ep/model.py#L1004-L1028) and skips router softmax, QB threshold estimation, per-expert counts, overflow summaries, and the [post-scan metric reduction](src/experiments/grug/moe_hero_ep/model.py#L1371-L1390). The expert indices and sigmoid combine weights used by the forward remain unchanged. | Model-specific |
| Hopper FA4 64×128 tile | The Levanter FA4 path chooses a generic tile from head dimension. The benchmark [overrides only the forward tile and thread count](src/exp586_moe/inference/jax_backend.py#L173-L201), selecting 64 query rows × 128 key rows with 128 threads for this H100, head shape, and 8,192-token causal/windowed mix. The attention algorithm and mask remain identical; the change improves occupancy and data reuse for this exact geometry. | Runtime-specific |
| Combine shared-expert GEMMs | The original model evaluates both always-on shared SwiGLU experts separately. The rewrite [concatenates their gate/up and down weights](src/exp586_moe/inference/jax_backend.py#L98-L117), then the [combined module](src/exp586_moe/inference/jax_backend.py#L45-L95) performs one input einsum, applies each expert's SiLU product to its slice, and performs one output einsum. This gives XLA two larger contractions instead of six smaller ones. It was an accepted milestone, but the final GEMM-fusion graph was slightly faster with the original representation. | Model-specific |
| GEMM fusion v2 (short) | Enables XLA's experimental [`--xla_gpu_experimental_gemm_fusion_v2=true`](src/exp586_moe/inference/optimized_jax.py#L8-L16) before backend initialization. The pass can fuse compatible GEMM-adjacent operations and choose a better generated graph for the static inference computation. The winning candidate disables the manual combined-shared rewrite and lets the compiler optimize the original expert structure, showing that the two approaches interact rather than stack automatically. | Runtime-specific |
| Long-run confirmation | This is the median of three fresh processes using batch 352, a 95% XLA memory pool, Sonic MoE, the selected FA4 tile, and GEMM fusion v2. The runs and range are stored in the [final confirmation summary](results/inference_optimization/final-confirmation-summary.json); their median supplies the 1,146,750 tok/s headline rather than relying on the preceding short candidate. | Measurement |
