## Entry Log

### 2026-10-08 - Initial implementation

- Hypothesis: The d768 Hero MoE can reuse experiment 582's DNA data, tokenization, pooled EP8 path, and evaluation protocol with architecture-specific LR scaling.
- Command: `uv run --locked --extra cpu pytest -q`
- Config: Ten epochs, global batch 64, Hero 1% linear warmup followed by linear decay to 5%; pretrained multipliers 0.5/1/2 and scratch multipliers 1/3/10.
- Result: 82 CPU tests passed and one GPU-only test was skipped on the first complete adapted suite.
- Interpretation: Static contracts pass; H100 compilation, source restore, routing, updates, and full-state restore remain to be qualified.
- Next action: Commit the reproducible project, validate one-node H100 canaries for both initializations, then qualify the production placement.

### 2026-10-08 - Two-node H100 runtime qualification

- [Pretrained routing smoke](https://forge.coreweave.com/wandb/eric-czech/marin/runs/exp586-plantcad2-d768-pretrained-routing-cf32-smoke-v1) completed 25 finite updates at roughly 297,000 input tokens per second with zero expert drops, a committed checkpoint, and successful three-way replay.
- Direct CoreWeave S3 reads verified the checkpoint and refreshed the operator credentials from Secret Manager after a stale local credential pair returned 403.
- Scratch compilation with default fusion autotuning did not produce an update within one hour.
- Disabling all GEMM and fusion autotuning and forcing four-way compilation produced the first scratch update quickly, but throughput fell to roughly 49,000 input tokens per second.
- The 25-update scratch diagnostic had no sender overflow and a final-20 mean receiver-drop fraction of 0.000375697, with a maximum of 0.003319174 when individual expert loads reached about 39 times their balanced mean.
- A fusion-autotuner-disabled control retains normal GEMM autotuning to measure whether it restores production throughput.
- A factor-64 receiver-capacity control allocated 84.86 GB per H100 and failed on its first train step when NCCL communicator creation reported CUDA out of memory.
- Factor 64 is therefore rejected; factor 32 remains the production candidate while a longer control tests whether its early receiver overflow settles.
